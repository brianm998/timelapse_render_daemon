# s1090 — TRD-16 engine loop, snapshots, problems and events

Summary: trd-core's engine runs start-up and the tick (guard, config reload, scan, EXIF, queue, promotion) and publishes a revision-stamped §6.10 snapshot whenever its content changes, with controls applied through one async handle.

What changed:
- `engine.rs`: `Engine` owns the store, config, tools, scanner, render queue, histograms, problems and snapshot. `Engine::new` returns the engine and an `EngineHandle` (controls over an mpsc channel, the snapshot on a `watch` channel). `startup`, `tick`, `apply` and `run` are callable directly, so tests drive it without the run loop.
- Start-up is split: `startup` resolves the tools; `begin` (re-adoption, the Swift history import, the stale partial sweep) runs at the first tick that has Full Disk Access and a loaded config. Retention runs only once a config is loaded.
- While Full Disk Access is missing a tick reads nothing: no config reload, scan, reap, promotion, EXIF job or `file_exists` probe. The phase is `PHASE_WAITING_FOR_DISK_ACCESS` even before a config has been read.
- `snapshot.rs`: the §7 types in plain Rust (`Snapshot`, `SequenceCard`, `VariantRow`, `RenderedVideo`, `FailureCard`, `Counts`), the §6.10 `in_progress` order, the stage and phase rules, the count-mismatch note, and the 60 s `file_exists` cache.
- `problems.rs`: the problem set keyed by stable id (`fda`, `tool:<name>`, `config`, `config-issues`, `codec:<name>`, `path:<path>`), keeping `since_ms` while a problem persists and sorting errors first. The config problems are not reported until a tick has read the config.
- `events.rs`: `EVENT_CONFIG_RELOADED`, written only when a reload leaves a loaded config; the six TRD-12 names are unchanged.
- `controls.rs` (outside the ticket's file list, required by §6.11 step 3 and A10): `pause_all_rendering`, `pause_sequence` and `pause_variant` all skip adopted foreign renders, so only a render's own `StopRender` ends one. A card can show `STAGE_PAUSED` while its adopted render keeps running; `foreign_render_left_alone` covers this. See the decision record.
- `tests/engine.rs`: the ten named tests (`lifecycle`, `ordering`, `fda_blocks_scanning`, `config_reload_event`, `phases`, `problems_lifecycle`, `snapshot_counters`, `count_mismatch`, `file_exists_cache`, `foreign_render_left_alone`), plus `fda_at_launch_waits_before_config` and `retention_uses_loaded_config`. They use the fake ffmpeg and a `/bin/sh` EXIF stand-in in temporary directories, with manual clocks and a fake process table.

Decisions:
- The revision goes up by exactly one per published change of content, and a tick or control that changes nothing keeps it. `generated_at_ms`, the revision and the last-scan timing are not part of the comparison.
- The phase precedence is starting, waiting for disk access, no config, paused, rendering, exporting, idle. Waiting comes before no config because the config cannot be read while access is missing. Starting ends at the first tick, not the first scan as §6.10 says: see the decision record.
- While Full Disk Access is missing the engine clears the scan (nothing is listed) and changes nothing on disk, and a running render is neither reaped nor signalled until access returns.
- A sequence with more exported frames than its raw sequence is kept out of the queue, so it never renders; it is listed as `STAGE_COUNT_MISMATCH` with the §6.10 note.

Verification: `cargo test -p trd-core` passes (all test binaries, including the twelve engine tests); `cargo clippy -p trd-core --all-targets -- -D warnings` and `cargo fmt --check` pass; `check-spdx.sh` and `check-test-names.py --ticket TRD-16` pass.
