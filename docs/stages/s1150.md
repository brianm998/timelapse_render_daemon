# s1150 — TRD-20 CLI client commands and `trd status`

Summary: every §5 client command now runs against a running `trd` over loopback, `trd status` prints the Activity view as text (newest first, Perl-style bars), `trd pair --json` prints the §5 object, and `trd scan --once` lists complete sequences and their outputs offline without a daemon.

What changed:
- `cli.rs`: the client commands, each a current-thread runtime and a `TrdServiceClient` over `http://<--address>`. Nothing answering is exit 2 with `trd is not running on <address>`; an RPC error is `trd: <message>` with exit 1. `status [--watch] [--plain]`, the pause/resume/render/retry/pause-all/resume-all/rescan controls, `failures [--dismiss | --dismiss-all]`, `config show|path|validate|set-path`, `pair [--json]`, `devices [--revoke]`, `log [-f] [--level] [--limit]`, and `scan --once [--config]`. `service` stays unimplemented (exit 1).
- `status_view.rs`: pure rendering of a `Snapshot` into lines: header, problems, failures, in progress (card line, bar and frames, export path, note, variant lines), recently rendered (newest 10). Colour only when `log_in_color`, a terminal and not `--plain`.
- `bin/trdw.rs`: includes `status_view.rs` by path, as `cli.rs` now needs it.
- `Cargo.toml`, `Cargo.lock`: `chrono` (already locked through trd-core) for the local UTC offset, and `crossterm` (workspace pin 0.28) for the alternate screen and clearing in `--watch`.
- `tests/cli_client.rs` (new): golden text for a fixture snapshot, `client_uses_test_address`, control commands read back through gRPC and `config show`/`config path`, pairing and device revocation, `log` ordering, `scan --once` over a temporary tree (no writes; existing outputs skipped), and `config validate` offline.
- `tests/cli.rs`: the not-implemented case moves from `status` to `service status`.

Decisions:
- `--watch` uses crossterm for the alternate screen, clearing and cursor moves, and `WatchSnapshots` at 2 per second.
- `scan --once` with no `--config` uses the default config path of §6.13; `config validate` with no file asks the running daemon for its path.
- `failures --dismiss` and `render`/`retry` are tested through their refusal paths (unknown ids); an effect test needs a failed or running render, which the sandbox fixture cannot produce.
